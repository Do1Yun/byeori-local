# byeori 로컬 LLM 전환 현황과 개선 검토

후속 구현 안내: 이 문서는 `a9228f0`의 검토 기록을 보존한다. 같은 날 적용한 1차 안정화와 검증 결과는 [수정 명세서 22절](LOCAL-LLM-REMEDIATION-SPEC-2026-10-01.md#22-1차-안정화-구현-결과--2026-10-01)에서 확인할 수 있다. 아래 재현 결과는 수정 전 기준이다.

검토일은 2026년 10월 1일이며, 검토 대상은 `a9228f0`이다. 원본 비교 기준은 로컬 전환 직전 커밋 `30a3045`이고, 그 이후의 로컬 개발 커밋 18개를 검토했다.

**개발 방향은 타당하다. PDF 등록부터 전문 추출, 노트 생성, 검색, 인용 답변까지 로컬에서 이어지는 기반을 만들었고, 원본 AWS 경로를 보존했다. 다만 현재 상태는 논문 처리와 품질 개선을 위한 개발용 런타임이다. 원본 byeori의 다중 논문 지식 시스템을 대체하거나, 생성된 수치를 검토 없이 연구에 사용하는 단계에는 도달하지 않았다.**

다음 작업의 우선순위는 기능 확대보다 기존 근거와 작업 상태를 정확하게 보존하는 것이다. 이번 검토에서 일괄 처리 누락, 확정 메타데이터 소실, 질문 작업의 대기와 동시 실행, 인용 범위 및 해시 검증 결함을 재현했다. 별도로 기존 11편 평가에 기록된 47개 결함을 해결하고 평가 범위를 넓혀야 한다. Concept와 Overview 생성은 이 기반을 정리한 뒤 붙이는 편이 좋다.


## 기존 논문 평가에서 확인된 품질 문제

[기존 평가 문서](evaluation/README.md)를 검토표에서 다시 집계한 결과는 동일했다. 11편 모두 `qwen3:8b`로 생성됐고, 생성 경로는 single 8편과 chunked 3편이다. 추출 상태는 complete 6편, partial 5편이다.

| 구분 | 주장 수 | 해석 |
| --- | ---: | --- |
| 평가에 포함된 주장 | 208 | 주로 기여·방법·결과·한계 절의 줄 단위 주장 |
| 인용틀림 | 21 | 값은 논문에 있으나 인용한 문단에 없음 |
| 수치틀림 | 9 | 수치·지표·대상·실험 조건을 잘못 결합하거나 근거 없는 값 사용 |
| 무인용 | 17 | 개별 주장에 문단 인용 없음 |
| 1차 검사가 플래그했지만 맞음으로 기록 | 13 | 축자 인용 실패, 버전 번호를 측정값으로 처리하는 등의 거짓 경보 |
| 자동 supported이며 추가 판정 없음 | 148 | 정확하다고 확정한 주장이 아님 |

기록된 결함은 47개로, 평가에 포함된 208개 중 22.6%이다. **이 수치는 사람 검증을 마친 전체 오류율이 아니다.** 판정자는 모두 `보조 (사람 확인 필요)`이며, 148개 supported 주장에는 추가 판정이 없다. 표·요약 등 검토표에서 빠지는 내용도 있으므로 이를 모델 정확도 77.4%나 원본보다 낮은 정확도의 증거로 사용해서는 안 된다.

특히 [scFoundation 검토표](evaluation/hao-2024-large-scale-foundation-model-on-single.md)는 PCC 개선을 AUC 개선으로 적은 경우를, [HEIST 검토표](evaluation/madhu-2025-heist-a-graph-foundation-model-for.md)는 ligand-receptor 예측의 AUC를 임상 예측에 붙인 경우를 기록한다. 숫자가 원문 어딘가에 있다는 검사만으로는 이 문제를 해결하지 못한다. 수치와 지표·대상·조건을 함께 보존해야 한다.

무인용 17개는 현재 게시 규칙이 개별 주장보다 절에 적용되기 때문에 통과한다. `validate_note`는 2~4절에 인용이 하나씩 있는지를 확인한다. 답변도 유효한 인용이 하나라도 있으면 다른 무인용 문장을 함께 반환할 수 있다. 기존 평가에서 발견한 이 문제를 게시와 답변 단계의 수정으로 연결할 필요가 있다.

메타데이터도 구분이 필요하다. 평가에서는 Attention 논문이 2023년으로, Bahdanau 논문이 2016년으로 기록됐다. [Attention의 공식 arXiv 기록](https://arxiv.org/abs/1706.03762)은 최초 제출 2017년과 해당 PDF의 마지막 개정 2023년을 구분하고, [Bahdanau의 공식 기록](https://arxiv.org/abs/1409.0473)도 최초 제출 2014년과 개정 이력을 별도로 제공한다. PDF에 나타난 날짜를 무조건 출판 연도로 쓰거나, 외부 DB의 값을 무조건 우선하면 모두 잘못될 수 있다. `publication_year`, `preprint_year`, `version_date`를 구분하고 사람이 정정할 경로를 두는 것이 좋다.

### R01 일괄 처리 대상이 조회 제한에 가려짐

[store.py](../src/byeori/local/store.py)의 `papers`는 최근 100편만 반환한다(L233). [service.py](../src/byeori/local/service.py)의 `pending`, `process_all`, `refresh_all`이 이 조회를 그대로 사용한다(L691, L695, L897). 따라서 최신 100편을 처리한 뒤에는 오래된 미처리 논문이 계속 남아 있어도 일괄 작업이 할 일을 찾지 못한다.

운영용 전체 순회와 화면용 목록을 분리해야 한다. 미처리 논문은 DB에서 직접 조건으로 조회하고, 목록은 페이지네이션을 제공하면 된다. 유사하게 `revalidate_all`은 최근 job 200개, orphan 질문 탐색은 최근 job 1,000개에 한정되므로 오래된 대상도 처리할 수 있도록 바꾸는 것이 좋다.

### R02 재조회가 기존 확정 메타데이터를 지움

[service.py](../src/byeori/local/service.py)의 `_refresh`는 기존 노트의 확정 메타데이터가 아닌 원래 TEI 추출값에서 다시 시작한다(L913). 조회가 disabled·not_found·unavailable이면 year와 work ID를 빈 값으로 만들고 새 revision을 게시한다(L917). 새 값이 없어도 이전 값을 지운다는 문제가 있다. 재현에서는 식별자에 2021이 남은 채 프론트매터와 검색의 연도만 사라졌다.

기존 확정값을 기본으로 삼고, 성공적으로 확인한 새 값만 갱신해야 한다. 재조회 실패는 별도 `lookup_status`로 남기고 확정값은 유지한다. 실패나 불확실한 조회 때문에 품질이 낮아지는 revision을 자동 게시하지 않도록 회귀 테스트를 추가해야 한다.

### R03 질문 작업 수명과 전체 실행 순서가 보장되지 않음

[jobs.py](../src/byeori/local/jobs.py)의 worker는 빈 큐를 읽으면 종료한다(L62). 그 읽기와 실제 종료 사이에 `submit`이 들어오면 `_ensure_worker`는 아직 살아 있는 thread를 보고 새 worker를 만들지 않는다(L55). 새 질문은 queued에 남고 해당 프로세스의 PID는 살아 있으므로 orphan 복구도 처리하지 못한다. 다음 제출 전까지 작업이 진행되지 않는 상황을 재현했다.

또한 `QuestionJobs`마다 자체 thread와 lock이 있고, [store.py](../src/byeori/local/store.py)의 `claim_question`은 실행 중 질문의 유무나 제출 PID를 고려하지 않는다(L280). 두 MCP 클라이언트나 CLI와 MCP가 같은 워크스페이스를 사용하면 모델 호출 두 건이 겹칠 수 있다. 논문 worker의 파일 lock도 질문이나 audit 호출과 공유되지 않는다. 이는 문서가 설명하는 워크스페이스당 질문 하나라는 계약과 다르다.

장기간 살아 있는 worker와 condition으로 대기·깨우기를 관리하거나, 큐 조회와 worker 종료 결정을 같은 동기화 범위에서 처리해야 한다. 프로세스 간에는 worker 소유권과 lease를 기록하고, 모델 호출을 공통 스케줄러에서 제한하는 것이 좋다. 단일 장비에서 실행 순서를 통제하는 작업이며 분산 큐 도입까지 필요한 것은 아니다.

### R04 인용이 실제로 제공된 근거와 연결되지 않음

[service.py](../src/byeori/local/service.py)의 `_paragraphs` 설명은 노트가 실제로 인용한 문단을 확인한다고 되어 있지만, 구현은 추출 JSON의 모든 문단 ID를 반환한다(L1244). P0001만 인용하는 노트에서 답변 모델이 P0002를 쓰면, 그 원문은 모델에 전달되지 않았는데도 답변을 반환한다. 개별 문장의 인용 유무도 검사하지 않는다.

긴 논문에서도 같은 범위 문제가 있다. `_write`는 일부 digest 실패 블록을 생략한다(L1115). 이후 검증은 생략 전 전체 블록을 기준으로 한다(L765). 재현에서는 P0007을 생략했는데 모든 주요 주장이 P0007을 인용하는 노트가 게시됐다. 실제 원문을 읽어 의미를 검증한 결과는 아니며, 제공하지 않은 근거를 인용하는 동작을 확인한 것이다.

답변에 사용할 수 있는 문단은 그 답변에 전달한 노트의 인용이나 추가로 제공한 원문으로 한정해야 한다. 부분 생성도 사용 가능한 ID와 생략 ID를 최종 생성·검증 단계에 전달하고 생략 ID는 인용할 수 없게 해야 한다. 중요 결과·방법 블록의 생략은 단순 블록 개수 비율로 허용하지 말고 재추출하거나 검토 필요 상태로 남기는 것이 좋다.

### R05 해시 기록과 읽은 파일의 내용이 다를 수 있음

[store.py](../src/byeori/local/store.py)의 `note`는 DB에 기록된 `note_sha256`과 현재 읽은 파일을 대조하지 않는다(L406). `integrity_problems`도 주로 파일 존재와 포인터·job·색인 관계만 확인한다(L423). 추출 JSON을 읽는 `context`와 `_paragraphs`도 내용의 해시를 확인하지 않는다.

이 때문에 파일 변경 후에도 이전 해시를 포함한 인용을 반환할 수 있다. 원본 PDF는 등록·처리 시 해시 검증이 있으므로 좋은 기반이 있지만, 노트와 추출에도 같은 연결이 필요하다. 작은 노트는 읽을 때 해시를 대조하고, 추출 JSON 자체의 해시도 기록하는 것이 좋다. 전체 원본·추출·노트 검사에는 `check --deep` 같은 별도 모드를 두고 기본 점검과 구분하면 된다.

### R06 Ollama를 사용한다는 사실만으로 로컬 추론을 보장하지 못함

[llm.py](../src/byeori/local/llm.py)는 HTTP(S) URL과 모델 이름을 받고, doctor는 tags의 이름이 일치하는지를 확인한다(L81, L117). cloud 모델·원격 추론 표식을 거부하는 로직은 없다. 실제 클라우드 호출을 한 것은 아니며, mock에서 그런 모델 항목을 받아들이고 chat 요청까지 하는 동작을 확인했다.

Ollama는 앱·CLI에서도 cloud 모델을 제공하며, 공식 문서는 로컬 모델만 사용하려면 cloud 기능을 끄도록 안내한다. 서버 설정의 `disable_ollama_cloud` 또는 `OLLAMA_NO_CLOUD=1`을 지원한다. [Ollama Cloud 문서](https://docs.ollama.com/cloud), [cloud 비활성화 안내](https://docs.ollama.com/faq#how-do-i-disable-ollama-cloud-features)

현재 Bedrock으로 자동 fallback하는 코드가 없는 점은 좋다. 여기에 모델 실행 위치 확인을 더해야 한다. cloud 모델은 거부하고 기본 URL은 loopback으로 제한하며, LAN의 로컬 추론 서버를 쓰는 경우는 명시적 설정으로 허용하는 방안을 권한다. 모델 이름 규칙만으로 판정하지 말고 설치 모델의 메타데이터와 서버 설정을 함께 확인해야 한다. OpenAlex의 외부 메타데이터 조회와 LLM 추론 위치는 별도 설정으로 다루면 된다.

### R07 성공 receipt를 확정 전에 기록함

[service.py](../src/byeori/local/service.py)는 publish 호출 전에 `outcome: succeeded` receipt를 쓴다(L779). DB 게시가 실패한 뒤 실패 receipt를 다시 쓰려고 해도 `_save_receipt`가 기존 파일을 덮어쓰지 않아 최초 성공 기록이 남는다(L1160). DB 확정 단계에 장애를 주입했을 때 이를 재현했다.

검색·활성 노트·job 성공이 DB 트랜잭션으로 함께 확정되는 동작은 유지된다. 파일 자체는 DB 트랜잭션 전에 기록되므로 실패한 작업의 파일이 남는 것은 허용할 수 있지만, 그 파일의 receipt가 성공을 뜻하면 안 된다. 실행 receipt와 게시 결과를 분리하거나, 마지막 결과를 쓰는 시점을 바꾸고 DB에서 실제 성공 여부를 확인하는 방식이 필요하다.

### R08 검토 판정이 달라진 근거에도 적용됨

[cli.py](../src/byeori/local/cli.py)의 `recorded_verdicts`는 주장 문장만 키로 삼는다(L48). 노트 revision, 인용 문단, 원문 텍스트가 달라져도 문장만 같으면 이전 판정을 새 검토표로 옮긴다(L111). 인용틀림을 고쳐도 잘못된 판정이 남거나, 기존 맞음 판정이 틀어진 인용에 붙을 수 있다.

판정 키에 논문 ID, 주장 텍스트, 정렬한 인용 ID, 근거 텍스트 해시를 포함해야 한다. 근거가 바뀌면 이전 판정은 이력으로 보여주고 새 판정은 비워 두는 것이 좋다. 원래 모델 설정이 바뀌더라도 동일 주장과 동일 근거의 판정을 보존하는 것은 가능하다.

### R09 검토표가 표와 일부 절을 평가에서 제외함

[service.py](../src/byeori/local/service.py)의 `review_sheet`는 `|`와 `>`로 시작하는 줄을 건너뛰고(L843), 2~5절만 대상으로 삼는다(L811). 표에 적힌 수치, 인용문 형태의 주장, One-line Summary와 Related Work·Glossary는 현재 평가에 포함되지 않는다. 여러 문장이 한 줄에 있으면 한 주장으로 묶이기도 한다.

Markdown 표의 각 데이터 행과 인용문도 원래 위치를 유지한 평가 항목으로 추출해야 한다. 장기적으로 노트 생성의 중간 결과를 구조화하면 단순 줄 분리의 한계를 줄일 수 있다. 우선 평가 보고서에 어떤 절과 표현이 포함·제외됐는지 명시하고, 현재 208개를 전체 노트의 모든 주장 수로 취급하지 않아야 한다.

### R10 중복 정의가 후반 구현을 숨김

[service.py](../src/byeori/local/service.py)에 `format_blocks`, `parse_tei`, `parse_metadata`, `GrobidExtractor` 등을 포함한 함수·클래스 16개가 각각 두 번 정의되어 있다. 전반 정의는 L68 부근, 후반 정의는 L334 부근부터이며, 큰 중복은 `f696b77`에서 추가됐다. Python에서는 후반 정의가 해당 이름을 덮어쓴다.

당장 모든 테스트가 통과해도 앞부분을 수정한 사람이 실제 동작을 바꿨다고 오해할 수 있다. 먼저 중복을 제거하고, 추출·노트 검증·질문·평가를 작은 모듈로 나누는 것이 좋다. 현재 `service.py`는 1,252줄이다. CI에 동일 범위의 이름 재정의를 탐지하는 정적 검사를 추가하면 이런 변경을 쉽게 잡을 수 있다.

### R11 실패한 CLI 작업이 종료 코드로 드러나지 않음

[cli.py](../src/byeori/local/cli.py)의 ask는 실패 job을 JSON으로 출력한 뒤 공통 `return 0`으로 끝난다(L228, L237). 모델 오류를 주입했을 때 상태 failed와 종료 코드 0을 확인했다. batch도 실패 수를 출력하는 것과 종료 코드의 의미가 구분되어 있지 않다.

job failed·interrupted는 실패 종료 코드, 정상적인 insufficient_evidence는 성공 종료 코드로 구분하는 것이 좋다. 일부 실패 batch는 별도 종료 코드나 명시적 정책을 제공해야 자동 실행에서 결과를 신뢰할 수 있다.

## 평가와 기록에서 추가로 개선할 부분

**모델 비교는 같은 논문과 같은 추출을 사용해야 한다.** 현재 자료만으로는 로컬 모델이 원본 모델보다 얼마나 못하는지, chunked가 single보다 얼마나 틀리는지 판단할 수 없다. 논문별 난이도도 다르고 supported 주장 대부분이 미검토 상태다. 먼저 현재 모델에서 동일 논문의 single과 chunked, 개선된 근거 묶음 방식을 비교하고 이후 다른 로컬 모델을 시험하는 편이 효율적이다.

**실행 기록을 재현할 만큼 완전하게 만들 필요가 있다.** 현재 `_process`의 `prompt_sha256`은 원문 블록으로 만든 body를 해시하며 시스템 지침과 최종 합성 prompt는 포함하지 않는다(L755). 모델 tag는 기록하지만 실제 모델 digest, Ollama 버전, 코드 commit, 호출별 think 옵션과 소요 시간도 필요하다. 질문과 audit 호출에는 노트 생성과 같은 수준의 설정·토큰·prompt 기록이 없다. 모델 tag를 갱신했을 때 동일한 이름의 다른 모델로 평가가 달라지는 상황을 구분할 수 있어야 한다.

**메타데이터 조회 실패를 정상적인 미발견과 구분해야 한다.** `OpenAlexLookup`는 HTTP 오류를 빈 결과로 바꾸므로 rate limit이나 서버 장애가 `not_found`로 기록될 수 있다. 현재 공식 API는 무키 기본 조회를 허용하고 무료 key로 예산을 높이며, 429에는 backoff를 권한다. mailto만으로 처리량을 유지한다는 현재 설명도 최신 문서에 맞춰 정리하고, key 설정·상태별 재시도·마지막 성공 결과 캐시를 추가하는 편이 좋다. [OpenAlex 인증과 제한 안내](https://help.openalex.org/api/authentication/)

**현재 개발 문서를 실제 상태에 맞춰 갱신해야 한다.** [LOCAL-DEVELOPMENT.md](LOCAL-DEVELOPMENT.md)는 모델의 이해 품질이 아직 평가 대상이 아니라고 설명하면서 하단에서는 평가 진행을 안내한다. OpenAlex가 연도·학술지를 확정하고 `extracted_year` 등을 보존한다는 일부 설명도 현재의 빈 값 보완과 `openalex_year` 불일치 기록 방식과 다르다. 검토표에는 CLI에 없는 `byeori-local read_paper_context` 안내도 있는데, 이 기능은 현재 MCP 도구다. 수정된 기능과 제한을 같은 문서에서 읽을 수 있도록 맞춰야 한다.

**백업과 재개는 기능 확대보다 먼저 운영 가능하게 만들어야 한다.** 원본은 워크플로와 체크포인트를 사용하지만 로컬은 중단된 논문을 처음부터 다시 처리한다. 이미 저장한 추출·digest를 검증 후 재사용하고, catalog·원본·revision·runs를 묶어 복구하는 절차가 필요하다. 파일을 보존한다는 정책만으로 단일 장비 장애 후 복원할 수 있는 것은 아니다.

## 권장하는 다음 개발 순서

### 먼저 상태와 근거 보존 결함 수정

R01~R06을 우선 수정하고, R07·R08은 같은 안정화 작업에 포함하는 편이 좋다. 각 재현을 기대 동작을 검사하는 회귀 테스트로 바꾼다. 코드 중복 제거는 후속 수정이 잘못된 정의에 들어가지 않도록 초기에 수행한다.

이 단계의 완료 기준은 101편 이상이 빠짐없이 처리되고, 재조회 실패가 확정값을 지우지 않으며, 모든 질문이 실행되거나 명시적으로 종료되는 것이다. 같은 장비의 모델 호출 수가 제어되고, 변경된 파일·제공하지 않은 문단·생략한 블록이 유효한 근거로 통과하지 않아야 한다. receipt와 CLI 종료 코드도 실제 결과와 일치해야 한다.

### 이어서 주장과 근거를 함께 생성

현재 digest와 노트가 사실과 문단 ID를 자유 형식으로 다시 쓰면서 귀속을 잃는다. digest의 중간 산출물을 `claim`, `metric`, `value`, `unit`, `condition`, `paragraph_ids`, `quote` 같은 필드로 묶고, 노트 작성 단계가 이 묶음을 사용하도록 시험하는 것을 권한다. 표시 형식은 지금의 Evidence Note를 유지할 수 있다.

프로그램은 인용 ID, 근거 문장 존재, 값·단위 연결과 제공 범위를 확인하고, 의미 판정은 별도 평가로 남긴다. 검증 가능한 근거 문장을 요구하면 오류를 줄일 수 있지만 문장의 존재만으로 지표·조건 귀속까지 증명되지는 않는다. 기존 audit도 자동 승인기가 아니라 검토 순서를 정하는 도구로 유지하는 것이 맞다.

모든 주장을 모델로 다시 검사하는 비용을 줄이려면 무인용·알 수 없는 ID·해시 불일치 같은 명확한 문제부터 코드로 거른다. 중요한 숫자와 비교 조건을 우선 검사하고, 알려진 수치 오류가 있는 노트는 일반 검색용 확정 노트와 구분된 검토 상태로 관리하는 방안을 권한다.

### 질문이 필요한 원문을 확인하도록 확장

검색 상위 3편 전체 노트를 한 번에 넣는 현재 방식에서, 관련 결과·방법·한계를 문맥 예산 안에 선택하고 필요한 원문 문단을 추가하는 흐름으로 확장한다. 원본 [evidence_packet.py](../src/byeori/evidence_packet.py)의 section 선택과 version 고정 개념을 재사용하되, S3 전용 접근은 로컬 저장소 adapter로 분리한다.

첫 구현은 검색, 관련 노트 읽기, 필요한 원문 문단 읽기, 인용 답변의 짧고 제한된 흐름이면 충분하다. 여러 검색이나 원문 확인이 끝나도 근거가 모자라면 그 범위와 이유를 기록한다. 작은 모델에 원본의 모든 편집·종합 도구를 한 번에 맡기는 방식은 현재 장비와 검증 수준에 비해 범위가 크다.

### 고정 평가 세트로 개선 효과 확인

기존 60개 플래그 항목은 사람이 확인하고, 148개 supported 항목도 무작위 표본과 중요 수치부터 확인한다. 표·요약·반례·조건이 평가에서 빠지지 않게 범위를 보완한다. 기존에 지적한 47개 결함이 실제로 고쳐졌는지 동일 근거로 비교하고, 새로 만든 노트의 판정은 별도 이력으로 유지한다.

평가에는 정확도만 아니라 주장 인용 비율, 수치·지표·조건 오류 수, 누락된 핵심 주장, 거짓 경보, 작업 실패·재시도, 시간·메모리를 함께 기록한다. 모델과 추출·코드 버전을 고정하고, 개선에 사용하지 않은 논문을 별도로 남겨 일반화도 확인한다. 수용 기준은 평가 전에 정하되, 여기서 제안하는 기준은 제품 정책이며 현재 검증된 성능 수치가 아니다.

### 그 뒤 다중 논문 위키와 지속 운영 구현

검토 가능한 노트가 쌓인 뒤 기존 Glossary 기반 Concept 후보 추출부터 연결하고, Concept와 Overview에 member note revision을 기록한다. 노트가 바뀌면 관련 종합 문서를 오래된 상태로 표시해 갱신 대상이 드러나게 해야 한다. category·카탈로그·backlink도 함께 연결해야 원본 byeori의 지식 누적 기능에 가까워진다.

동시에 목록 페이지네이션, 색인 재구축, 검증된 백업·복원, 중간 재개, 장기 worker 실행과 로그를 준비한다. 로컬 설치를 찾기 쉽게 README의 첫 안내와 패키지 설명·릴리스 기록도 정리한다. AWS 저장소 연결이나 다중 사용자 기능은 개인 로컬 워크플로가 안정된 뒤 별도 범위로 진행하는 편이 좋다.

## 현재 상태에 대한 판단

**기술 방향은 잘 잡혔고, 실측에서 배우면서 구현을 수정한 과정도 좋다. 현재 부족한 것은 로컬 실행 가능성보다 결과의 신뢰성과 작업 수명의 안정성이다.** 지금은 원본의 핵심 입출력 흐름을 로컬에 옮긴 상태이고, 원본의 원문 재독·다중 논문 종합·지식 누적·지속 운영 기능은 남아 있다.

다음 성과는 기능 개수보다 확인한 결함의 해소로 판단하는 것이 좋다. 먼저 이 보고서의 구현 재현이 정상 동작으로 바뀌고, 기존 수치·인용 결함이 고정 평가에서 줄어드는지를 확인한다. 그다음 검토된 노트를 기반으로 Concept와 Overview를 만들어야 로컬 LLM을 사용하는 byeori라는 목표에 안정적으로 가까워질 수 있다.
